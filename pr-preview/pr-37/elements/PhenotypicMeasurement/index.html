    Class: PhenotypicMeasurement

    A measurement of a phenotypic trait of an organism or observation unit: one trait value, produced by one method, at one time. Modeled on MIAPPE v1.2 Observed Variable (trait + method + scale) and on the ORNL APPL plant phenotyping exports, where one Observation row is one trait value from one imaging event.

    Comments

    • Deliberately thin. Measurement already carries what phenotyping needs: the trait's name goes in observed_property or property_label, the method in measurement_method, the summary in statistic, the image-QC state in quality_flag, missing values in missing_value_reason, and computed traits (pixel counts times a calibration scale, such as APPL's millimetre areas) in value_role derived. Only the trait-ontology hooks are new.
    • Phenotype versus measurement: a raw trait value (projected shoot area on one date, Fv/Fm from one fluorescence event) is a measurement and belongs here. An interpreted phenotype claim ("dwarf under high dose"), aggregated over many measurements, is a knowledge-level assertion and is deliberately NOT this class; value_role interpreted covers a single interpreted value, and a future Phenotype class referencing the measurements it derives from would cover the aggregate. Flagged as an open question on the genotype/strain straw person.
    • QC values that describe the measuring process rather than the organism (for example APPL's fc1.mask_coverage_pct segmentation coverage) should be plain Measurements, not PhenotypicMeasurements, so trait tables are not polluted with instrument diagnostics.
    • A known APPL pitfall this model should not reproduce: events whose segmentation found no plant (empty_mask) store 0.0 instead of no value. Here that case keeps the source's 0.0 in raw_value only, with missing_value_reason not_determined and quality_flag empty_mask, so no parsed numeric_value fabricates a size for a plant that was not seen.
